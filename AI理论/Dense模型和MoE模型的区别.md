# Dense模型和MoE模型的区别

## 一句话结论
- Dense：每个 token 都会经过几乎全部参数，结构简单、训练与部署稳定，但算力随参数线性增长。
- MoE（Mixture of Experts）：把大模型的参数拆成多个“专家”，每个 token 只激活少量专家（Top-k 稀疏激活），在相近 FLOPs 下可拥有更大总参数与更强容量，但训练/并行/路由更复杂、系统开销更高。

> [!info] 记住两个维度
> - 总参数（capacity）：MoE 通常能做得很大（很多专家参数加起来）。
> - 每 token 计算（FLOPs/compute）：MoE 只用少量专家，因此计算可控；Dense 则随模型规模整体上升。

## 基本概念

### Dense（稠密模型）
- 典型形式：[[Transformer]] 的标准 FFN/Attention 都是稠密计算（全连接 + 全量参数参与）。
- 对每个 token：前向会用到该层的全部权重（或几乎全部权重）。

### MoE（混合专家）
- 思想：把某些子模块（最常见是 FFN）替换成多个“专家网络” + “路由器/门控（router/gate）”。
- 对每个 token：路由器给专家打分，只选择 Top-k 专家计算并加权聚合。

一个常见抽象：

$$
y(x)=\sum_{i \in \text{Top-}k(g(x))} g_i(x)\,E_i(x)
$$

其中 $g(x)$ 是路由器输出的权重（通常带归一化），$E_i$ 是第 $i$ 个专家。

## 结构差异（参数使用方式）

### Dense：参数“全参与”
- 每层的 FFN/Attention 都对所有 token 做同样的稠密矩阵乘。
- 参数利用率：每 token 使用几乎全部参数。

### MoE：参数“按需激活”
- 专家数量多，总参数大，但每 token 只走少量专家。
- 参数利用率：每 token 使用的参数是稀疏子集，但跨 token/批次整体能覆盖更多参数。

> [!tip] 为什么 MoE 能“总参数更大但计算不爆炸”
> 因为稀疏激活：把“容量”与“计算”部分解耦——总参数大不代表每 token 都要算完。

## 计算与成本（训练/推理）

### 训练成本
- Dense：
  - 计算：随参数规模、序列长度、batch 增长，整体规律更线性、可预测。
  - 并行：数据并行/张量并行/流水并行方案成熟。
- MoE：
  - 计算：理论 FLOPs 由 Top-k 决定，但会引入路由开销、all-to-all 通信、以及负载不均衡带来的浪费。
  - 并行：专家并行（expert parallel）常见，需要更复杂的通信编排。

### 推理成本
- Dense：
  - 延迟：结构规则，kernel 更容易优化，延迟稳定。
  - 吞吐：适合大规模 batch 和成熟推理引擎。
- MoE：
  - 延迟：路由 + 通信会放大尾延迟（尤其是小 batch、跨节点场景）。
  - 吞吐：在大 batch、专家分布良好且通信优化到位时可能很强；否则可能被系统开销抵消。

## 表现与泛化（能力来源）

### Dense 的优势
- 训练更稳：优化目标更“均匀”，不容易出现某些参数长期得不到梯度更新的问题。
- 泛化更直觉：参数共享更充分，迁移/微调流程更简单。

### MoE 的优势
- 更高容量：更容易把不同类型知识/技能分散到不同专家中，提升上限。
- 计算效率潜力：在相近每 token compute 下，模型总参数可更大，从而提升效果（但依赖系统实现与训练稳定性）。

> [!warning] 常见误解
> “MoE 一定更快/更省钱”不总成立：如果通信、负载均衡、专家缓存等做得不好，实际成本可能更高。

## 关键工程问题（MoE 特有）

### 1) 负载均衡（load balancing）
- 如果路由器总偏向少数专家，会导致：
  - 热点专家过载（排队、延迟上升）
  - 其他专家闲置（算力浪费、参数训练不足）
- 常用手段：负载均衡损失、容量因子（capacity factor）、噪声路由等。

### 2) 通信模式（all-to-all）
- token 需要被分发到对应专家所在设备，专家输出再回收聚合。
- 多机多卡时尤其敏感，通信可能主导时间。

### 3) 稳定训练与专家退化
- 专家可能出现“塌缩”（很多 token 跑去同一两个专家）。
- 一些专家训练不足，等效容量没用起来。

### 4) 可控性与可解释性
- 有时能观察到专家分工（例如语言/代码/数学倾向），但这种分工并不总是稳定可控。

## 适用场景（怎么选）

### 更偏向 Dense 的情况
- 追求部署简单、延迟稳定、工程风险低。
- 规模不需要极端大（总参数可控），或硬件/通信条件一般。
- 需要更简单的微调、蒸馏、量化、推理加速链路（生态成熟）。

### 更偏向 MoE 的情况
- 目标是更高的能力上限，且能投入系统工程（通信/并行/调度）优化。
- 训练/推理是大规模集群环境，能 amortize all-to-all 的开销。
- 任务/数据多样性高，希望不同专家形成“分工”以提升容量利用。

## 对比表（速查）

| 维度 | Dense | MoE |
|---|---|---|
| 每 token 参数参与 | 高（几乎全参与） | 低（Top-k 专家参与） |
| 总参数扩展 | 计算随之显著增加 | 可大幅增加（容量扩展） |
| 训练稳定性 | 高 | 中-低（需要路由/均衡手段） |
| 系统复杂度 | 低 | 高（路由 + all-to-all） |
| 延迟稳定性 | 高 | 受通信/负载影响 |
| 典型替换位置 | Attention/FFN 都可稠密 | 常见仅替换 FFN 为专家 |
| 适合人群 | 想要“稳、好部署” | 想要“更大上限、愿意折腾系统” |

## 与其他概念的关系
- MoE ≈ 一种 [[稀疏激活]] / [[条件计算]]（Conditional Computation）的实现方式。
- MoE 不等于“稀疏注意力”：MoE 通常稀疏的是 FFN 专家选择，注意力仍可稠密（也可以做稀疏注意力，但不是同一件事）。

## 常用术语小词典
- Expert：专家子网络（常见为 FFN）。
- Router/Gate：路由/门控网络，决定 token 去哪些专家。
- Top-k：每个 token 选择 k 个专家（常见 k=1 或 2）。
- Capacity factor：每个专家最多接收的 token 数上限，用于防止溢出与控制负载。
